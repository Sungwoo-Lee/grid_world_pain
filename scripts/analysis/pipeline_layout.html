Analysis Pipeline Layout

Three programs read the same trajectory store today, each re-implementing the same scan and each carrying a different subset of the safety checks. Here is what that looks like, and what one shared scan would look like instead.

Where the code is now

Every study so far has written its own scan of the trajectory store: open the shards in order, work out where each episode begins, line up predictors with outcomes, filter, accumulate. The three that exist were written months apart, and each picked up whichever correctness checks its author had in mind that day.

Those six checks are not stylistic. Each exists because getting it wrong produces a plausible wrong number rather than an error:

Nine of the seventeen applicable cells are empty. Two of the three bugs this analysis hit sit in an empty cell: the time course was silently rebuilt from stale data because nothing cross-checked its population, and a third of episodes containing no predator were binned into the comparison group because nothing filtered absent animals.

The duplication that motivates the change is not in doubt: slot_layout is implemented three times, smell_channels three times, listcol three times, nociception_kernel twice, and the two copies of the store finder have already drifted apart — one handles a single root, the other several.

What it would look like instead

One program owns the scan. Everything a study writes sits above it and never touches a shard.

What changed after review, and why

The first draft proposed a declarative mini-language — a study would describe its accumulators and never write a loop. The reviewer showed that will not survive contact: the existing sweeps build crossed two-dimensional grids, composite geometry conditions, quantile-derived bin edges, and a within-episode convolution with a reset boundary that no per-row primitive expresses. Either the language grows a dozen constructs or the escape hatch becomes the normal path — and an abstraction everybody bypasses is worse than none.

So the design above is a scan driver with a callback, not a language. The driver owns everything that has gone wrong before — shard order, episode boundaries, the t=0 rule, the previous-row rule, the population contract — and hands the study a frame it can trust. What the study does with that frame is ordinary NumPy, written in the study's own folder, where its author can see it.

Two decisions that are yours, not mine

Scope — now decided. Two older folders, scripts/analysis/figures/ (9 scripts) and scripts/analysis/supplementary/ (19 — not the 9 the dependency map claims, a separate correction that map owes), hold the third copies of the duplicated helpers and back the earlier trajectory-factors study. They are frozen: a note in each README saying they predate core/ and are kept to reproduce that study as published. The honest consequence, stated rather than glossed: two copies of the duplicated helpers survive, not one. Porting them would double the work for no new capability.

Moving about 25 files under scripts/ obliges a same-commit update to SCRIPTS_DEPENDENCY_MAP.md, whose repo-root and sys.path depth hazard applies directly to from analysis.core import scan. Two documents also name script paths that will move.

Timing. The seed replication is the natural first client of this core, which argues for building it now, before a fourth scan gets written for it. It is also days that are not spent on the replication itself. That trade is a portfolio call.

How a port is checked

Rewriting code that produces published numbers needs a mechanical check, not a careful reading. But the obvious check — require identical output — cannot be used, and finding out why changed the plan.

Why "identical output" is the wrong gate

The three scans use three different NumPy primitives for the same logical sum: np.add.reduceat, np.bincount and np.add.at. These are not bitwise equivalent on floating-point data — addition is not associative in floating point, and they accumulate in different orders. A unified driver necessarily changes that order, so a correct port would fail the test on every float column. The gate would then be renegotiated after the fact, on exactly the numbers behind the published ladder analysis.

The criterion instead, fixed before any porting starts rather than after seeing a diff

Two conditions on the baseline. It must be fresh — the goldens on disk predate the second collection pass, so the comparison is old-code-run-today against new-code-run-today on the same store. And the goldens must be protected: ported code writes to a scratch path, because the naive port would overwrite the very files it is being compared against.

Order of work

Each step leaves the repository working. hiding_drivers.py is on the ladder's critical path — figures 6 and 7 read its output — so nothing is deleted until its replacement has passed the gate.

  1. Build core/ alongside the existing code, changing nothing that runs.
  2. Regenerate the goldens with the current code, today.
  3. Port build_arm_data; compare under the criterion above.
  4. Port build_time_course, then hiding_drivers; same gate each time.
  5. Only once all three pass, delete the old implementations.
  6. Port the fifteen figure scripts, comparing plotted arrays.
  7. Freeze figures/ and supplementary/ with a note in each README.

Honest cost

The reviewer's estimate, which I accept over my own: two to four days, not one. My figure budgeted nothing for the verification sweeps — three sweeps across fourteen arms, run twice, to compare old output against new — nor for porting fifteen gated figure scripts.

And the verification gate needs restating. I proposed requiring byte-identical output, which cannot hold: the three programs use three different NumPy summation primitives for the same logical sum, and those are not bitwise equivalent on floating-point data, so a correct port would fail the test. The workable version is bit-exact for integer-valued counts, a pre-registered tolerance for float accumulations, and equality of plotted data rather than image bytes.
