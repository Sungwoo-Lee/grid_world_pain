Analysis Pipeline Layout

How a trajectory store becomes a published figure, one stage at a time — every script named by its real path, with the code that does the work. This describes the pipeline as it exists and runs today, not a proposal.

What this is

The project trains agents, records what they did into a store of Parquet files, and turns that into figures and a shareable page. The turning-into-figures half is what this page documents.

It runs in five stages, and the reason it is worth drawing is that the stages have very different shapes. One stage reads hundreds of gigabytes and takes minutes per arm. Three stages read a few megabytes of JSON and take seconds. Knowing which is which is most of what you need to work on this code without waiting on it: if you are changing how a figure looks, you never touch the slow stage.

Every path below is real and every code block is copied verbatim from the file it names, so you can open any of them and find what you see here.

What this page is not

An earlier version of this page argued for reorganising this code — replacing the three separate store-reading programs with one shared scan. That refactor was reviewed twice and then parked, and none of it is built: there is no core/ package and the three programs still each read the store themselves. The argument, its costed plan, and the conditions that would restart it live in docs/develop/active/refactors/analysis_pipeline_refactor.md.

This page now describes what actually exists, because that is what you need in order to run it, read it, or add to it. The duplication is still real and is described honestly at the end, but it is a footnote here rather than the argument.

The shape of it

Stage by stage

1 · The store — the input, not code

results/trajectories_lad/  +  results/trajectories_lad2/

452 GB · 3.32 billion step rows · 14 million episodes · read-only to everything below

Sharded Parquet, written once by the collector and never modified by the analysis layer. Two directories because the population was collected in two passes; each shard directory carries a _manifest.json recording every parameter the collection used, which is what made it possible to reconstruct the collection specs after the fact.

Nothing on this page writes here. If an analysis is wrong, re-running it costs minutes; the store is not at risk.

2 · The sweeps — the only code that opens the store

scripts/analysis/ladder/build_arm_data.py  ·  235 lines

one arm's store → results/analysis/ladder/<arm>.json · ~60-95 s per arm

Walks every shard once, and accumulates everything the fifteen figures will later need into counter arrays. The whole method is two NumPy primitives: reduceat to sum within an episode, and add.at to scatter into a bin.

red = lambda a: np.add.reduceat(a, st)

np.add.at(G["pd_bush"], (dpb[hp], ib[hp]), y[hp])
np.add.at(G["pd_tot"],  (dpb[hp], ib[hp]), 1.0)
np.add.at(G["dw_inj"], ib, y);   np.add.at(G["dwt_inj"], ib, 1.0)

Every quantity is stored as a pair — a numerator and its denominator, never a precomputed rate. That is what lets a figure choose its own grouping later without going back to the store, and it is why _ladder.rate() exists downstream.

scripts/analysis/ladder/build_time_course.py  ·  133 lines

one arm's store → results/analysis/ladder/time_course_<arm>.json · ~4 min per arm

4 · The figures — one script per figure, named for its number

scripts/analysis/ladder/lad01_ladder_overview.py … lad15_price_of_hiding.py

47-144 lines each · aggregates → docs/experiments/active/sensor_ladder/figures/<name>.png · seconds each

Fifteen independent scripts. The filename carries the figure number, so Figure 8 in the report is always lad08_*.py and the page's build refuses to ship a figure whose script is missing. Each one opens with a docstring stating its question, why it matters, and how it is computed — that docstring is the source of the "How it is computed" block on the published page, so the two cannot drift apart by being edited separately.

They all follow the same six lines of setup. Here is Figure 8's, verbatim:

import sys, os; sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
import numpy as np, matplotlib.pyplot as plt
import _ladder as L, _plot as PL

D = L.load_all(); arms = L.ARM_ORDER; col = PL.arm_colors()
x = np.arange(4)
curves = {a: L.rate(D[a]["grids"]["dw_early"], D[a]["grids"]["dwt_early"]) for a in arms}
slope = {a: curves[a][3] - curves[a][0] for a in arms}
GRP = {a: L.resolves_identity(D[a]["sensory"]) for a in arms}

That is the whole contract: load_all() for the aggregates, rate(numerator, denominator) to turn a stored pair into a percentage, and arm_colors() so every figure agrees on which colour means which arm. A new figure is a new file that starts with those lines.

scripts/analysis/ladder/make_report_tables.py  ·  163 lines

aggregates → markdown tables, consumed by the page builder

Emits every numeric table in the report so that no number in the document is typed by hand. It reads the regression output the third sweep wrote:

def glm(a, model, term):
    p = f"results/analysis/lad/{a}/multivariate.csv"
    for r in csv.DictReader(open(p)):
        if r["model"] == model and r["term"] == term:
            return float(r["dpp_per_sd"])
    return float("nan")

5 · The page — template plus real figures plus generated tables

scripts/analysis/ladder/build_artifact.py  ·  238 lines

template + PNGs + tables → docs/experiments/active/sensor_ladder/sensor_ladder.html (8.7 MB)

The prose lives in a hand-written template; the numbers and images do not. The builder substitutes two kinds of token and fails if any is left over, so a renamed figure is an error rather than a blank panel nobody notices.

html, scripts = attach_provenance(html)
html = re.sub(r"\{\{FIG:([a-z0-9_]+)\}\}", fig, html)
html = re.sub(r"\{\{TABLE:(\d+)\}\}", tab, html)

left = re.findall(r"\{\{[^}]+\}\}", html)
if left:
    raise SystemExit(f"unsubstituted tokens remain: {sorted(set(left))}")

It enforces a good deal more than substitution, and all of it as hard build failures rather than warnings: every figure must name an existing generating script and appear exactly once; every caption must carry an Axes. sentence and a "How it is computed" block; every figure must declare how much data it used; and the axes sentences mirrored into the markdown report must match the template verbatim, checked before anything is written so a stale copy cannot ship.

Running it

Two commands rebuild everything downstream of the store. The first is the slow one and is only needed when the store changes; the rest take seconds.

P=/home/vncuser/miniconda3/envs/grid_world_pain/bin/python

# stage 2 - slow, only when the store changes
$P scripts/analysis/ladder/build_arm_data.py       # ~60-95 s per arm, 14 arms
$P scripts/analysis/ladder/build_time_course.py    # ~4 min per arm, 14 arms

# stages 4 and 5 - seconds
$P scripts/analysis/ladder/run_all.py              # all fifteen figures
$P scripts/analysis/ladder/make_report_tables.py   # every table in the report
$P scripts/analysis/ladder/build_artifact.py       # the shareable HTML page

Both sweeps take --arms to rebuild a subset, which is what makes a fourteen-arm rebuild parallelisable across nodes. The figure runner is twenty-four lines and exists only to save typing — each figure script still runs standalone:

for f in sorted(glob.glob(f"{HERE}/lad*.py")):
    try:
        runpy.run_path(f, run_name="__main__")
        print(f"[ok] {n}  {time.time()-t:.1f}s", flush=True)
    except Exception as e:
        fail.append((n, repr(e)))
if fail:
    print("FAILED:"); [print(f"  {n}: {e}") for n, e in fail]; sys.exit(1)

It runs every figure even after one fails, then exits non-zero with the list — so one broken figure gives you the other fourteen plus a report, instead of stopping at the first traceback.

Adding a figure

  1. Check the quantity you need is already in <arm>.json. If it is, you never touch stage 2, and your edit-run loop is seconds long.
  2. Create ladNN_short_name.py with the six-line preamble above. The number must match the figure's number in the report.
  3. Open with a docstring giving the question, why it matters, and how it is computed — the published page's method block is built from it.
  4. Save through PL.finish(fig, path) so the DPI and margins match the others.
  5. Add the {{FIG:ladNN_short_name}} token to the template with an Axes. sentence, and mirror that sentence into the markdown report. The builder fails if either is missing or if the two copies differ.

If the quantity is not in the aggregates, you are adding a counter to stage 2 and re-running the sweep — minutes per arm, not seconds. That is the one expensive kind of change, and it is worth checking first.

The wart, stated plainly

Stages 3, 4 and 5 share code. Stage 2 does not. The three sweeps were written months apart and each re-implements the same scan, so several helpers exist in more than one copy: slot_layout three times, smell_channels three times, listcol three times, nociception_kernel twice, and the store finder three times — and those copies have already drifted, one handling a single store root and the others several.

They also carry different subsets of the same safety checks. Nothing forces them to agree, and they do not: of the twenty applicable cells, ten are still empty.

Why this matters more than ordinary duplication

Every one of these checks exists because getting it wrong produces a plausible wrong number rather than an error. Three bugs in this pipeline have been of exactly that kind: a third of episodes with no predator being binned into the comparison group; a rebuild silently running on stale data because nothing cross-checked the population; and a dose-response reading its predictor from the wrong row. All three produced figures that looked fine.

None was caught by a test. Two were caught by review and one by a reader noticing a number that could not be right.

The costed plan for fixing this — one guarded scan with a callback, instead of three — is in docs/develop/active/refactors/analysis_pipeline_refactor.md. It was reviewed twice, revised three times, and then parked: it produces no new scientific result, the study it would have protected is finished, and all three bugs above have since been fixed in the existing scripts. It restarts when a fourth program needs to read the store, which is the point at which someone has to choose again which of the checks to remember.
