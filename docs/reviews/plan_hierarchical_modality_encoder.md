# Plan review — Modality-hierarchical encoder/decoder for dreamer_srl

> **Reviewed by**: plan-reviewer · 2026-07-28
> **Object**: [[hierarchical_modality_encoder_plan]] (`docs/develop/active/dreamer_srl_v2/hierarchical_modality_encoder_plan.md`, commits `96bd746` → `361cbcd`)
> **Verdict**: **NOT READY AS WRITTEN — one 🔴 blocker, unilaterally fixable.** Flips to SOUND WITH CONCERNS the moment the implementer amends the file-edit protocol described under B1. Tonight's autonomous chain **can proceed without waking the user** once B1's remedy is adopted.

## Verdict (plain language)

The plan proposes giving our in-house DreamerV3 world model the same "one small network per sensor" input structure our recurrent-PPO baseline already has (seven sensor groups — hunger level, two pain channels, smell, touch, last movement, vision — each with its own branch before fusion), with two decoder variants, all behind a config switch whose default keeps today's architecture byte-for-byte. The architecture, config-validation, and test design are sound and were verified against the actual code. The one blocking problem is operational, not architectural: the plan asserts that every file it edits is only *imported* by the live training jobs (safe to edit, since imported modules are held in memory) — but two of the files it touches are **launched as fresh processes from the shared NAS checkout** by the eight live recurrent-PPO runs' during-training evaluation pipeline and by any running probe sweep. Editing those files overnight, in place, can crash those freshly-spawned evaluations — and the failure is silent, because the trainer dispatches them fire-and-forget. The fix is a small edit-protocol change the implementer applies alone; no human decision is needed.

## 🔴 B1 — The Live-jobs-safety claim is false for the eval scripts (and for fresh re-imports of `agent.py`)

**The plan's claim** (§Live-jobs safety): "All edited files are imported (held in memory) by the 4 live node-114 dreamer jobs, not hot-read."

**Ground truth** ([SCRIPTS_DEPENDENCY_MAP.md](../environment/SCRIPTS_DEPENDENCY_MAP.md) §1b): `train.py` (the rPPO trainer running ~8 live jobs on nodes 107/108/110/112) subprocess-dispatches `scripts/eval/experiment_eval_checkpoint.py` at every Nth checkpoint save when during-training experiment eval is enabled, and that script subprocess-runs `scripts/eval/eval_rollout.py --config-list`. Dwell-sweep workers (`sweep_worker.sh`) also spawn `eval_rollout.py` per checkpoint. Every such spawn is a **fresh Python process reading the current NAS copy** of `eval_rollout.py` *and freshly importing `src/algorithms/dreamer_srl/agent.py`* (branch-local import in the Dreamer branch). "Imported files are safe" holds only for already-resident processes, not for processes spawned after the edit.

**Failure scenario**: the developer edits `eval_rollout.py` (File Change 3) or `agent.py` (File Change 1) mid-evening; a live rPPO run hits its Nth checkpoint and spawns the eval chain, which reads a half-written file (NAS in-place write is not atomic) or hits a transient bug in the new code. The `subprocess.Popen` is async and never `wait()`-ed — the eval just silently never produces results. Eight runs' during-training eval data degrades for hours with no error surfaced, discovered days later at analysis time. This is precisely the "do not disturb live jobs" constraint the launch was conditioned on.

**Remedy (unilateral, pick both parts)**:
1. **Atomic replacement for every edited file** that any subprocess can read fresh (`agent.py`, `train.py`, `dreamer_srl_main.py`, and especially `scripts/eval/eval_rollout.py`, `dreamer_srl_probe_eval.py`, `visualize_dream.py`): edit a copy, then `mv` it over the original (same-directory rename is atomic; a mid-edit reader gets either the old or the new complete file, never a truncation). Before starting, run `pgrep -af "eval_rollout|experiment_eval_checkpoint|dreamer_srl_probe_eval"` locally and prefer an edit moment with no active spawn.
2. **Post-edit proof the rPPO branch still works**: immediately after the `eval_rollout.py` edit, run a python syntax check (`py_compile`) plus one real single-`--config` eval of an **existing rPPO checkpoint** and one of an **existing flat Dreamer checkpoint** on the local machine (`--device cpu`). Both consumers exercised; a break is caught in minutes instead of silently poisoning the night. Alternatively, File Changes 3–6 (eval-script plumbing) may be **deferred** out of tonight's window entirely: an un-updated eval script meeting a hierarchical checkpoint fails loudly by design (the plan's own `ValueError` on `hierarchical + observation_breakdown=None`), so deferral costs nothing tonight — but then the same atomic-write discipline still applies to `agent.py`/`train.py`, which fresh eval spawns re-import.

**Exit condition**: the implementation step adopts remedy 1 (and either runs remedy 2's smoke pair or defers File Changes 3–6). With that amendment the verdict is SOUND WITH CONCERNS and the chain proceeds.

## 🟢 Nits

- **N1** — Design 2's trunk-sizing key source: the flat decoder actually reads the **encoder's** `dense_units`/`mlp_layers` (`agent.py:2057-2061`, the quirk the plan itself documents at §call-sites), while the plan's design section says the heads-decoder trunk reads `decoder.*` keys. Identical at XS (both 256/1); make `HeadsMLPDecoder` read the same source as flat so designs 1 vs 2 differ only in the head, or say in D-018 that they intentionally diverge.
- **N2** — Give the hierarchical modules attribute names disjoint from flat's (`output_head` vs e.g. `heads`) — the plan implies this; keeping it guarantees no accidental subset relationship in the Orbax tree, which is what makes cross-mode restore fail loudly.

## ❓ Unstated assumptions (audited)

1. **Modality slice order is stable** — VERIFIED by construction: `get_observation_breakdown` (`sensor.py:350-390`) mirrors `get_observation`'s assembly order (`sensor.py:290-343`) flag-for-flag, and rPPO's branched encoder has depended on exactly this ordering since `train.py:1021`. The planned `sum(breakdown) == obs_dim` assert catches width drift but not an equal-width permutation; the curriculum fingerprint pre-flight (`dreamer_srl_main.py:723-769`) covers stage-level drift. Residual risk low; shared with rPPO.
2. **Eval consumers learn `encoding_mode` from the run** — VERIFIED: training saves the resolved agent config to `models/agent_config.yaml` (`dreamer_srl_main.py:977-983`); `probe_eval` and `eval_rollout` rebuild from `--agent-config` pointing at it, and `probe_eval` already computes the breakdown (`dreamer_srl_probe_eval.py:188`) — File Changes 3–6 are one-line pass-throughs.
3. **Cross-mode checkpoint restore fails loudly** — verified by design, pending the plan's own test: `PyTreeRestore(partial_restore=True)` tolerates checkpoint-extra keys only; target keys absent from the checkpoint error, and both eval consumers wrap restore in a raising `try/except` (`eval_rollout.py:1493-1507`, `probe_eval.py:223-234`). The historical silent-partial-restore bugs (Known Bugs H1, L3) were in rPPO `train.py` and the deprecated `evaluation.py`, both fixed; the live path is immune. The plan's "flat-checkpoint-into-design-2/3 raises" test must actually run before launch — it is the empirical check of this assumption.
4. **No existing config newly fails the flat+`hierarchical_params` ValueError** — VERIFIED: `grep -rn "encoding_mode\|hierarchical_params" configs/models/dreamer_srl/ configs/train/` is empty, so the new validation cannot break any existing config, `extends:` layering included (a hierarchical child *adds* keys to a flat base; no removal semantics needed).
5. **The in-flight `dsrl_b03_XS_bins6_rr0p25` run is a valid design-1 control** — holds only if (a) the new configs are diff-identical to it except the network block (whoever authors them must diff against the control's *saved* config, not its source YAML) and (b) the flat-parity gate passes, so File Change 7's train-step edit didn't change flat training. Note the control, running pre-change code, will **lack** the new `wm/recon_mse/*` per-key metrics — per-key reconstruction comparisons need a future flat rerun; survival-step comparison is unaffected.
6. **Launch uses the CLI budget flags** — `dreamer_srl` single-config mode reads its budget from `env_cfg.training.*` and exits almost immediately unless `--episodes` is passed on the CLI (auto-memory gotcha). The training-runner must carry the same CLI flags as the two live bins±6 runs.
