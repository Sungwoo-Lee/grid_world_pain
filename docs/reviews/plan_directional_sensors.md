# Plan review — DIRECTIONAL_SENSORS_PLAN

**Object**: [[DIRECTIONAL_SENSORS_PLAN]] (`docs/develop/active/sensors/DIRECTIONAL_SENSORS_PLAN.md`)
**Reviewed by**: plan-reviewer
**Date**: 2026-08-19

## Verdict

**NOT READY** — one Critical finding in the visual-mask semantics; the engineering core (kernel, olfactory diamond, parity tests, cost claims) is sound and well-evidenced.

Plain-language summary: the plan adds two opt-in sensor upgrades — smell sampled on a small diamond of points so it carries a direction, and vision blurred along the line of sight so distance becomes vague while bearing stays sharp — with everything off by default and byte-identical observations promised for the shipped config. Most of it holds up: the kernel math matches the study's working prototype, the "blur costs nothing" claim is backed by a real measurement, and the parity claims survived my own bitwise micro-checks. The blocker is the new per-entity invisibility option. The plan justifies its masking design with "'hidden' should mean no leakage", but the mechanism it specifies does leak: a `far`-masked ("hidden") entity still deposits a deterministic signal into the cell the agent stands on — about 13.5% of a visible adjacent entity's peak signal when the hidden entity is one cell away, fading only as 1/d². A recurrent agent can learn to detect a "hidden" predator from that leak, which would silently invalidate any future experiment built on the premise that the agent cannot see it — the wrong conclusion would look exactly like the interesting result ("anticipatory avoidance of an unseen threat"). The plan's own test suite would cement the leak as specified behaviour. The fix is cheap now: gate on the *entity's* distance (zero its whole column) or re-specify what `far` means and have the user sign off.

Severity legend: 🔴 Critical = fix before going further · 🟡 Moderate = likely costs a re-run · 🟢 Low = cosmetic · ❓ Open = an assumption nobody has verified yet.

## The three unilateral decisions (audit requested by the caller)

| Decision | Verdict | Basis |
|---|---|---|
| Normalisation by full analytic mass | **Supported.** | Fig 4's measured numbers (over-diamond normalisation removes distance falloff entirely: 0.513/0.698/0.486 at d=1/2/4; full mass gives 0.262/0.161/0.032). The alternative silently deletes the feature's point. Bonus the plan could state: full-mass normalisation gives vision an intrinsic ~1/d² fade, so no separate decay term is needed. |
| One width + anisotropy ratio ρ | **Supported — and equivalent to the study's own preference.** | σ_⊥ = (scale/ρ)·d is linear in d, i.e. exactly the study's "fixed angular blur" (Δθ = arcsin(scale/ρ)) under different knob names, with ρ=1 giving the isotropic ablation as a single config value. The floor breaking proportionality at short range is documented as intended. No overreach here. |
| Mask after blur (per-cell gate) | **Not supported — the rationale is inverted.** See finding 1. | The study explicitly left this Open; the chosen option leaks into the centre cell while the row's justification claims no leakage. |

One caveat the plan dropped: the study marks **sensor range as "Blocking — every question above resolves differently at range 1 than at range 3"**. Deferring the *values* to experiment configs is legitimate for an implementation plan, but the plan should say that the shipped defaults (scale 0.5, ρ 3, floor 0.5) are placeholders whose sanity was studied at specific ranges, not blessed training values.

## Open assumptions (❓)

- **a. Out-of-bounds diamond cells.** `sense_olfaction_cells` applies no in-bounds mask: an agent at a wall samples the chemical field at points *outside the world*. Physically coherent (the field is defined by distances) but undecided — the visual sensor zeroes OOB cells, collision marks them; olfaction would be the only sense that reads through walls. Nobody chose this.
- **b. The on-source decay-2.0 rule.** `sense_resource` returns decay 2.0 when the sampling point sits on a source (`sensor.py:14`). Today only the agent's own cell can trigger it; with per-cell sampling any diamond cell can, so it fires routinely. OLFACTORY_EXPANSION_STUDY lists this as **Open ("Keep, or make it continuous?")**; the plan silently resolves it to "keep" by reusing `sense_resource` unchanged, without listing it in the decision table.
- **c. Fingerprint coverage is inconsistent.** The three continuous blur knobs are deliberately traced (good, CP5) but therefore absent from the fingerprint — two curriculum stages differing in ρ or scale (a large same-dim semantics change) pass validation, while a `visual_blur_enabled` flip is rejected. Also pre-existing and adjacent: `visual_vector_size` is not fingerprinted, so a compensated swap (e.g. olfactory range +20 dims vs visual V 8→28 at range 0) passes both checks today; the same edit could close it.
- **d. Blur-curriculum foreclosure.** Fingerprinting `visual_blur_enabled` forbids a "train sharp → continue blurred" curriculum by construction. That is the check's documented purpose (no semantic swaps across stages), but it is a capability being removed before anyone asked for it — worth one line to the user.

## Cost of being wrong

If finding 1 ships as specified, the first masking experiment produces a paper-level wrong conclusion that is indistinguishable from the hoped-for result (an agent "anticipating" a hidden predator it can actually faintly see) — that is the expensive one, and it is two lines of spec to fix now. Finding 2 costs a confused day and an unplanned config sweep the first time anyone re-evaluates a pre-change run — loud, recoverable, but currently undisclosed. Everything else is caught at test time and costs minutes.

## Exit conditions (what flips the verdict)

1. Resolve `far` semantics: entity-distance gating, or re-specified leak semantics with explicit user sign-off (finding 1).
2. Disclose and decide the old-config/old-run consequence, and add the standalone-config sweep to File Changes (finding 2).
3. Re-point `test_modality_fingerprint.py` at the case only the fingerprint catches, and CP6 at the implemented code (findings 3, 4).

Findings 5–7 and the ❓ items are author's-discretion improvements; they do not gate the verdict.

**Owners**: finding 1 → user decision, then `senior-developer` (plan revision); findings 2–7 → `senior-developer`; ❓a/❓b → user (design calls the studies left open); no `bug-curator` items — nothing here contradicts the Known Bugs registry, and no new latent bug in existing code was found beyond what the plan already flags.
