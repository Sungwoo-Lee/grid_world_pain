# Cross-phase generator coordination — BACKLINKS-block exclusion rule

## Key conclusion

When two scripts both read insight bodies — one to inject content (e.g., `regen_wiki_graph.py` writes BACKLINKS blocks), one to mirror author intent (`regen_wiki_links.py` parses `[[id]]` tokens into `related:` frontmatter) — the second script MUST exclude the first script's injection regions before scanning, or it will treat auto-generated content as author intent. This creates a self-amplifying cycle: the link regenerator picks up backlink mirrors → adds them to `related:` → the graph regenerator picks up the new `related:` IDs → injects them into more BACKLINKS blocks → next link-regen run picks them up again. The fix is to define a clear injection-region marker (HTML comment) and strip it in every body-scanning consumer.

## Evidence, measurements, facts

- The bug surfaced at Phase C's verification gate. Phase C's developer ran `python scripts/regen_wiki_links.py --check` (expected exit 0 — idempotent), got exit 1 with 16 files that would be modified. None of Phase C's edits caused it.
- Investigation: Phase B (`regen_wiki_graph.py`, lines 206-211) already had a `BACKLINKS_BLOCK_RE` regex stripping the block before scanning for `[[id]]` tokens — correct, because Phase B's own injection would have caused the same self-amplification. But Phase A (`regen_wiki_links.py`) was written before BACKLINKS existed and did NOT have the strip.
- Confirmed by reverting all Phase C work and re-running `--check` against the post-Phase-B HEAD: same 16 files. So the bug was pre-existing, just not surfaced until Phase C ran the verification gate.
- Fix: hotfix commit `33f98b6` — `BACKLINKS_BLOCK_RE` added to `regen_wiki_links.py`, mirrored from `regen_wiki_graph.py`. 12-line change. Post-fix: both regenerators' `--check` exit 0; running either then the other produces no diff.

## Decisions and actions

- **Adopted invariant for `docs/llm_wiki/`**: any script that scans insight bodies for author-intent markers (`[[id]]`, `[link](url)`, frontmatter cross-references, etc.) MUST strip auto-generated injection regions first. Today the only such region is BACKLINKS; future regenerators that inject content (e.g., a hypothetical `regen_topic_summaries.py`) must use their own clearly-marked injection regions AND every body-scanner must update its strip-set.
- **Did NOT factor strip-helper to a shared module** — duplicated the regex constant + `re.sub` call in both scripts. Per project convention "no premature abstraction," two call-sites is below the abstraction threshold. If a third regenerator is added, factor then.
- **Verification gates for any new body-scanning script** should include: (a) `--check` idempotency on a clean tree; (b) re-run after `regen_wiki_graph.py` re-runs (catches BACKLINKS leak); (c) re-run after `regen_wiki_links.py` re-runs (catches `related:` round-trip).
- Phase A verification was repeated post-hotfix (Phase B section of the design doc verification report); both blocker gates passed at re-check.

## Open questions and follow-ups

- Should the lint script (`scripts/lint_wiki.py`) explicitly check for "no `[[id]]` token resolves to itself" (self-link via the leak) as a regression guard? Currently the lint checks `[[id]]` resolution but not the self-link case. Adding the check is 3 lines.
- If the corpus ever sprouts a third body-scanning regenerator, factor `BACKLINKS_BLOCK_RE` (or the broader injection-region pattern) into `scripts/_memory_common.py` or similar. Two duplicates is fine; three is the time.
