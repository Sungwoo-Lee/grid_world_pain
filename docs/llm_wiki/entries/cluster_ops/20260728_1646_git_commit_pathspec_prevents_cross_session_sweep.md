# Cross-session git safety — pathspec on commit, retry on lock

## Key conclusion

Staging by name does **not** stop a parallel session's staged files from landing in your commit; only putting a pathspec on the **commit** does. `git commit -F msg -- <files>` commits exactly those paths and ignores the rest of the index, which makes the sweep structurally impossible rather than merely unlikely. Separately, `.git/index.lock` contention on this NAS repo is not an anomaly to wait out: a plain `git status` takes the lock while refreshing the index and is slow here, so with three or four live sessions the lock is held much of the time. The correct response is to retry the operation with stderr visible — never to delete the lock, and never to gate the retry on a `[ ! -f .git/index.lock ]` check.

## Evidence, measurements, facts

- Confirmed recurrence of [[20260528_0218_git_lock_parallel_session_contamination]]: a `git commit` in this session swept in `docs/diary/2026-07-27.md`, which a parallel session's `developer` agent had staged but not yet committed. Commit reported "2 files changed" when only one was staged by this session.
- The pre-staging guard that had just been written to `CLAUDE.md` did **not** catch it: it checked `git diff` (unstaged) on the file being added. Foreign work was already *staged*, hence invisible to an unstaged diff. `git diff --cached --name-only` is the check that would have seen it.
- Harm was limited to attribution — the swept row was a complete diary entry, not half-finished work. Not reversed: `git reset --soft` on a contended index risks tangling the other session's in-flight commit, which is worse than misattribution.
- A retry loop of the form `if [ ! -f .git/index.lock ]; then git add … && git commit …; fi; sleep 3` failed 60 consecutive attempts over ~3 minutes, then `git add` succeeded on the very first try when run directly. The check-then-act window loses on a slow index. The loop also wrapped both git calls in `2>/dev/null`, so its failure reported a cause that had never been verified.
- Live process evidence: `ps` showed a parallel session's `git status --porcelain` running for 45 s, and `.git/index.lock` timestamps 17 s old — a fresh lock held by a real process, not a stale one.
- Zsh detail that broke a commit attempt: unquoted `$FILES` is **not** word-split, so `git add $FILES` passed 19 paths as a single pathspec and failed.

## Decisions and actions

- `CLAUDE.md`'s auto-commit rule now carries three layers: diff shared files before staging (content), commit with an explicit pathspec (index), retry on a locked index with stderr visible (contention).
- Of the three, only the pathspec is structural — the other two depend on remembering to be careful.
- Never suppress stderr on a git retry. The one time it was suppressed, the reported diagnosis was fabricated from the loop's exit code.

## Open questions and follow-ups

- Diary writes are `flock`-protected by `diary_append.py`, but shared instruction files (`CLAUDE.md`, agent profiles, the playbook) have no locking at all. A future `flock` wrapper for those edits would remove the class rather than document it.
