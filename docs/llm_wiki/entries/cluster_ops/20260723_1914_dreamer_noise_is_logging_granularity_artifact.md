# Dreamer-vs-rPPO curve "noise" is a logging-granularity artifact, and episode metrics are iteration-coupled

## Key conclusion
The impression that Dreamer training is "much noisier" than rPPO on WandB is almost entirely a **logging artifact**, not a property of the agent. Two compounding causes: **(1)** the word `log_interval` is measured in *iterations*, but an iteration means 128x different things — an rPPO iteration collects a full rollout (`num_steps 128 x num_envs 16 = 2048 env-steps`) while a Dreamer iteration is one env-step across all envs (`16 env-steps`). So the same `log_interval` number produces wildly different env-steps (and episodes) per WandB row. **(2)** Episode metrics are logged as a **block mean over "the episodes that finished inside the iteration-gated window," then the accumulator list is CLEARED** — so the smoothing window *is* the iteration-based `log_interval`, welding noise to cadence. The user's intuition that an episode metric should be iteration-independent is correct as a principle; the implementation couples them.

## Evidence, measurements, facts
- rPPO `log_interval: 500` iters x 2048 = **~1.02M env-steps/row** (~7,700 episodes/row); Dreamer at the value I ran (`--log-interval 100`) x 16 = **1,600 env-steps/row** (~12 episodes/row). Noise ~ 1/sqrt(n) => Dreamer dots carried ~25x the standard error.
- Code: `iteration_episodes.append(...)` accumulates, then at the log boundary `wandb.log(mean)` and `iteration_episodes = []` (dreamer `dreamer_srl_main.py:~1898`; rPPO `train.py` same pattern). Nothing ever logs raw per-episode values.
- rPPO's `tqdm` progress bar (with per-episode moving-average) does NOT survive to WandB — WandB collapses the carriage-return updates — so rPPO's WandB console shows only a banner + one `[CHECKPOINT]` line per save (~44 lines / 21h). A separate reason rPPO "looks clean."
- The tuned config value (`configs/models/dreamer_srl/01_food_only_buf256k.yaml`, `log_interval: 2000`, ~160 episodes/row) was silently OVERRIDDEN by my `--log-interval 100` CLI flag (priority: CLI > YAML > default). Same failure family as the num_envs CLI-shadow bug [[20260710_1632_num_envs_cli_override_config_owns_values]].

## Decisions and actions
- Designed and shipped a two-level logging redesign that decouples window (noise) from cadence (volume) — see [[20260723_1915_two_level_logging_and_config_layering]].
- Lesson reinforced: a bare unit-less knob (`log_interval` in iterations) is a repeated footgun; new knobs must carry their unit in the name.
- The stale memory [[20260529_1825_log_interval_anchored_rows_per_session]] ("~38 SPS, 20-40k eps/24h") is calibrated for `replay_ratio=1`; our `rr=0.0625` runs hit ~147 SPS / ~131k eps/24h (~4x) — it misled the analysis twice and needs correcting.
