# Node 114 NAS-mount intermittent for sustained I/O; gpu_status-free != NAS-usable

## Key conclusion
Two distinct traps on node 114 this session. (1) The NAS mount is per-node live state that can be broken while the node is up: an initial `run_command.py 114` failed with `mkdir: cannot create directory '/media/nas01/projects': Permission denied` (SSH connected, NAS write denied). After the user remounted, a df/mkdir check passed and a 100s probe dwell-sweep ran fine — but a longer video-eval job then HUNG (0 recordings in 35 min, the eval_rollout process alive but at 0% CPU = blocked on NAS I/O). So "NAS reads OK now" does not guarantee sustained writes hold. (2) `gpu_status.py --free` lists 114 as free because it queries GPUs over direct SSH nvidia-smi (not via the NAS), so a NAS-broken node still shows up as an available launch target.

## Evidence, measurements, facts
- Failure signature of the broken mount: `mkdir ... /media/nas01/projects: Permission denied` from run_command's log-dir creation, exit 255/1.
- Post-remount: `df | grep nas01` -> NAS_MOUNTED, repo file test -> REPO_OK, logs writable; nproc=64 (RTX 6000 Ada node).
- Hang signature: video job process present (`pgrep -fc curric_videos.py`=1, eval_rollout=1) with `/proc/loadavg` ~0 and zero recordings written after 35 min; the same script ran to completion in seconds/minutes when re-run LOCALLY.
- Mitigation used: ran the probe SWEEP on 114 (short bursts, worked twice) but ran the long video eval LOCALLY.

## Decisions and actions
- Standing practice: verify 114's NAS with a real write (df + a repo-file test) before a job, and for LONG eval/render jobs prefer a stable node or watch for a 0-output stall; do not trust `gpu_status --free` alone for 114.
- Do NOT hard-exclude 114 — it is per-node live state (same policy as node 107).
