# train.py does not resolve extends: -> training silently drops inherited config layers

## Key conclusion
train.py:369-373 loads the `--config` file with `Config.load_yaml` (= yaml.safe_load), which does NOT resolve the v3.0 `extends:` chain. The trained config is therefore `get_default_config()` + train/agent/eval defaults + ONLY the config file's own explicitly-written keys. Any layer a config inherits from a non-default `extends` parent (noise from basic/06, random-init + all-combined from basic/05, etc.) is dropped and falls back to default.yaml. Confirmed: basic/07's saved `models/config.yaml` has `perceptual_noise.enabled: false`, `random_start_injury: false`, hiding `count_high: 4` — all default, not the intended noise=true / random-init=true / hiding 2-12. Fix: load `--config` via `load_env_config(args.config)` (the same resolver eval_rollout and the tests use), verifying merge order vs the default/train/CLI merges and the continual `--configs-dir` path.

## Evidence, measurements, facts
- Reproducing train.py's load (get_default_config + Config.load_yaml(basic/07) + merge) == the saved config exactly (noise false, random-injury false, hiding 4). `load_env_config(basic/07)` gives the intended values (noise true, hiding 2-12).
- Scope: self-contained configs (basic/05 — full env/body in own file, extends only default) are CORRECT. Configs inheriting from a non-default parent (basic/06, basic/07, variants 01-05) trained wrong. This session's runs v1-v5, basic/07, jump-reach were all misconfigured; TERMINATED for relaunch after the fix.
- Bug latent since v3.0 extends layering landed (2026-06-19); TOOLING (eval_rollout, parity tests, ad-hoc verification) all use load_env_config, so configs always "looked" correct — masking the training bug.

## Decisions and actions
- Terminated all affected runs; developer implementing the load_env_config fix (with a load-identical assertion for basic/05/06/07 + variants) + relaunch after.
- HOW IT WAS MISSED (methodology lesson, now a CLAUDE.md Working Principle 'Verify actual state, not a re-derivation'): I verified the config FILE via load_env_config (the tooling loader that resolves extends), not the RUN's saved config; then 'confirmed' with an obs-noise test and an eval_rollout video that BOTH reuse load_env_config — echoing the same broken assumption back as proof. And I explained away the user's repeated 'no noise' observation twice instead of distrusting my model. Rule: inspect the ground truth the system produced; never confirm with a tool that shares the suspected-broken code path.
