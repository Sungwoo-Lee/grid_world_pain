# Dwell-sweep incremental re-run: two silent-skip traps

## Key conclusion
Re-running `scripts/eval/dwell_sweep/run_sweep.py` against an already-populated output dir can silently do (almost) nothing, in two independent ways: (1) a **stale-done-marker bug** — the worker `touch`es `_run_markers/done_<node>` at the END but never removed it at start, and `run_sweep.py` never cleared markers before launching, so `poll_done` saw the prior run's markers and reported "all nodes done in 1s" without waiting; the newly-launched workers kept running and, in a chained multi-spec run, stacked on top of the next spec's workers (CPU oversubscription). (2) a **watermark-poisoning gotcha** — the incremental logic only evaluates checkpoints with step > the max already in the CSV; a `--max-checkpoints 1` smoke test grabs the NEWEST checkpoint, sets the watermark to the max, and the subsequent full run then treats every OLDER checkpoint as done.

## Evidence, measurements, facts
- Marker bug: `sweep_worker.sh:~79 touch "$MARK/done_$NODE"` with no start-of-run `rm`; `run_sweep.py poll_done` checks `done_{n}` existence, no clear-before-launch. Symptom: an incremental GAE re-run enumerated 397 pending cells but printed "all 5 nodes done in 1s". Fix: `run_sweep.py` unlinks `_run_markers/done_{n}` for each launched node right before the launch loop (race-free: clear->launch->poll); `sweep_worker.sh` also `rm -f`s its own marker at start (defense). Verified: re-run now waits minutes, appends checkpoints oldest->newest (GAE b03 472->643, b04 489->723), no stacked workers.
- Watermark bug: the smoke wrote 1 checkpoint (the newest, e.g. step 20.6M) per (run,cond); the full NMN run then found only 26 pending cells instead of ~880 and produced ~8 rows/run instead of ~200. No force-rebuild flag exists — recovery is `rm -rf` the (freshly-created, gitignored) output dir and re-run clean; then enumeration restored to 930 cells.
- Rule: NEVER smoke-test a watermark-incremental sweep with `--max-checkpoints` against its REAL output dir; use a throwaway output dir. The incremental design assumes CSVs fill oldest->newest contiguously.

## Decisions and actions
- Committed the marker fix (`run_sweep.py` + `sweep_worker.sh` + README).
- Killed the broken chain + orphaned node workers (pkill -f matched its own shell — used explicit PIDs instead), then re-ran cleanly.

- None; a future `--force-rebuild` flag would remove the wipe-and-rerun workaround but wasn't needed.
