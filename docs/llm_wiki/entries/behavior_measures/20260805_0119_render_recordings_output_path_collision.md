# render_recordings.py output-path derivation collides in batch video jobs

## Key conclusion
`scripts/eval/render_recordings.py` has no output override; it writes mp4s to `run_root/videos/<rec_dir.name>` where `run_root = rec_dir.parent.parent`. When a batch job renders many curated selection dirs, two failure modes recur: (1) if the selection dirs all share a basename (e.g. `_selected`), every render lands in the SAME derived dir and overwrites; (2) the caller computes the wrong move-source (e.g. `sel.parent/videos` instead of `sel.parent.parent/videos`) and moves 0 files even though the render succeeded.

## Evidence, measurements, facts
- Hit this 4x this session: dp1 experiment-condition videos, curriculum probe+trainenv videos, and the bushrefuge trainenv videos.
- Working fix pattern: place each item's selected recordings at `<base>/_sel/<unique_key>` so `rec_dir.name == <unique_key>` and the derived `video_dir == <base>/videos/<unique_key>` is unique per item; then read/move from that EXACT derived path (not a hand-guessed one). Per-condition probe videos use `<label>/_sel/<cond>`; per-run trainenv videos use `videos_trainenv/_sel/<label>`.
- The trained-env variant is extra-easy to get wrong because `_sel` sits one level shallower, so `rec_dir.parent.parent` lands a directory HIGHER than the probe layout.

## Decisions and actions
- Worked around each time; recommended (to user, twice) adding an explicit `--output-dir` flag to `render_recordings.py` as the permanent fix. Not yet implemented (awaiting user go-ahead).

## Open questions and follow-ups
- Add `--output-dir` to render_recordings.py so batch callers stop reverse-engineering the derived path. Small, well-scoped.
