# A fresh empirical re-audit finds a bug class the first read-only pass missed

## Key conclusion

Re-running a whole-pipeline correctness audit — with a different model generation and, crucially, a **run-the-code rather than read-the-code** method — paid off strongly. Seven parallel reviewers re-verified every fix from the prior (Opus-era) audit as correct AND found **10 new High-severity bugs** the first pass missed. The new bugs were found by two techniques the read-only review didn't use: (a) **empirically executing the suspect path** (e.g. proving `--load-checkpoint` silently kept random weights by running restore and comparing leaves; proving an interrupted-feeding metric was structurally pinned at 0.0 by constructing the episode), and (b) **diffing a port against its upstream reference line by line** (finding the missing sheeprl reset block, the gradient-clipping gap). Lesson: a static review that reads code against a paper/reference does not catch integration-layer bugs; a second pass that executes the code and diffs against upstream does — and it is worth re-auditing with a fresh model even after a prior audit signed off. This echoes the 2026-05-12 pivot lesson that static plan-review didn't predict integration success.

## Evidence, measurements, facts

- Prior audit (Opus, 2026-07-04): found + fixed a large cluster; all its fixes re-verified correct this session (nothing regressed).
- Fresh re-audit (Fable 5, this session): 7 area reviewers, all fixes verified + 10 NEW High bugs (H1-H10). Examples caught only by execution/diff: H1 rPPO restore silently random-weights (proven by running restore), H4 MC returns truncated at rollout-window edge, H5 dreamer_srl terminal-reward bleed (found by diffing vs sheeprl's reset block), H8 eval CSV column shift (found by reading a real run's CSV), H9 offline interrupted-feeding rate structurally 0.0 (found by constructing the episode).
- The parity re-audit ([[20260723_1910_sheeprl_parity_drift_lives_in_glue]]) is the same method applied to the sheeprl port.
- Cost: this thoroughness burned significant tokens (Fable 5) — the session was deliberately run sequentially (one agent at a time) in later phases to respect token-rate limits.

## Decisions and actions

- Adopt "empirically execute + diff-against-upstream" as the default for correctness audits of ported / integration-heavy code, not read-only review.
- A fresh-model re-pass over already-audited code is worthwhile when the code is integration-heavy and the first pass was read-only.
