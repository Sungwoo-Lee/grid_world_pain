# Contended-GPU proxy benchmark hid a real -13% step-throughput regression

## Key conclusion
A proxy speed benchmark run on a **busy/contended** GPU mis-ranked the env change: it predicted step
throughput within +-3% (i.e. "noise, negligible"). A **clean idle-node** re-measure (node 104, 0% load)
showed a **real -13% step-SPS regression**, driven by the **+2 extra animal hot-path slots** (count_high
allocation is processed every step). Reset was +28-30% but is negligible in wall-clock (one reset per
~250-500 steps). Lesson: measure perf deltas on a **clean idle node with both run orderings** — a
contended-GPU proxy can bury a real regression in noise.

## Evidence, measurements, facts
- Proxy (shared node ~80% load): reset +3..+30% (the BASELINE itself drifted 6.6->8.6 ms between runs
  from other jobs), step SPS +-3%.
- Clean (node 104 idle, num_envs=128, both orderings; reset = median of 51 jitted/vmapped calls, SPS =
  best of 25 jitted lax.scan rollouts): reset ~1.0 -> ~1.33 ms (**+28-30%**); SPS ~2.15M -> ~1.87M env-steps/s
  (**-13 to -14%**). Both deltas track the config, not which compiled first (order-independent).
- Driver: **animals are the hot path** (per-step movement / sensing / distance over count_high slots);
  resources/obstacles cost much less per step. `per_type` placement gave no benefit at this entity count.

## Decisions and actions
- Surfaced the -13% as a user-owned speed-vs-variance tradeoff. User accepted the variance and **trimmed
  the rabbit high-bound 3->2** (one fewer hot-path animal) to recover ~half the regression; food/bush/rock
  variance kept. Reset +28% accepted as negligible.
- Trimmed-config SPS not precisely re-measured (estimated ~-7%); optional clean re-benchmark.
