# Float distributional ranges on integer distances: [2,3] != {2,3} (use [2,4])

## Key conclusion
`attack_range` (and `detection_range`) are sampled per-episode as CONTINUOUS floats via `jax.random.uniform(lo,hi)`, but they gate behaviour as `manhattan_dist <= range` where the distance is an INTEGER. So the effective integer reach is `floor(range)`. A narrow range like `attack_range: [2,3]` samples uniformly in [2.0, 3.0) -> floor is always 2 -> it is behaviourally IDENTICAL to `[2,2]` (distance 3 is never covered: `3 <= 2.7` is false). To actually get "sometimes reach 2, sometimes reach 3", set `[2,4]`: half the draws land in [2,3) (reach 2), half in [3,4) (reach 3). This is a config-authoring trap whenever you want a per-episode mix of two adjacent integer reaches on a float distributional field.

## Evidence, measurements, facts
- Empirical (predator at fixed distance, attack-timer as jump detector): `[2,2]` -> jumps @dist2 100%, @dist3 0%; `[2,3]` -> @dist2 100%, @dist3 **0%** (identical to [2,2]); `[3,3]` -> both 100%; `[2,4]` -> @dist2 100%, @dist3 ~46-50%.
- Surfaced when the user asked for a level-07 variant with "jump range [2,3]"; it would have been a near-duplicate of basic/07. Shipped as `basic05_variants/06-jump_range_2to3.yaml` with value `[2,4]` and a header explaining why.

## Decisions and actions
- Config convention: to get effective reach {k, k+1} on a float distributional field, set the range to `[k, k+2]`, not `[k, k+1]`. Document the value in the config header.
- Cleaner long-term fix (deferred): sample `attack_range` as an INTEGER (randint(lo,hi+1)) like move_interval/attack_delay, so a literal `[2,3]` means {2,3}. See [[20260703_0343_predator_jump_pounce_mechanism]].

## Open questions and follow-ups
- Whether to convert attack_range to integer sampling (would make [lo,hi] intuitive for reach) — user's call if jump reach is tuned often.
