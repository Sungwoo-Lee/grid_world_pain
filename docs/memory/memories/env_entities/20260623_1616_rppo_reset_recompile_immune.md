# rPPO reset-all-then-where is recompile-immune to per-episode count variance

## Key conclusion
The per-episode entity-count variance feature ([[20260623_0143_per_episode_count_variance_masking]])
does **not** trigger an XLA recompile storm under **recurrent_ppo (rPPO)**. Two independent reasons,
both confirmed: (1) the K-activation draws K as a **traced scalar** and builds **count_high-static**
masks, so K is a runtime value, never a shape; (2) rPPO's training loop **resets ALL envs every step at
a fixed (num_envs) shape and selects with jnp.where(done,...)**, so there is no variable-width reset.
This is the **opposite** of the Dreamer recompile storm ([[20260622_1746_dreamer_srl_recompile_storm_done_count]]),
which sized per-step reset arrays to the variable done-env count and compiled a new executable per width.

## Evidence, measurements, facts
- Activation builder `core.py::_build_activation_mask`: `K = randint(ek, (), lo, hi+1)` (scalar, traced);
  mask = `slot_rank < slot_K` over `num_slots = count_high` (static). No `dynamic_slice` by K, no array
  dimensioned by K, no Python branch on K. `has_range` is a Python-static bool baked into the trace.
- rPPO reset pattern `src/models/recurrent_ppo_trainer.py:177-183`: `vmap(jax_step)` over all num_envs ->
  `vmap(jax_reset)` over all num_envs -> `jnp.where(done, reset, continue)`. Constant (num_envs) shape every
  step. (`src/environment/wrapper.py::auto_reset_step` is the same shape-stable pattern.)
- Empirical probe (CPU, `JAX_LOG_COMPILES=1`, ranged default.yaml, N=32 envs, 800 steps spanning many
  episode resets with different K each): the jitted env reset+step `env_iter` compiled **exactly once**
  (warmup at step 0) and produced **zero recompiles** across the remaining 799 steps. A K-sized-array bug
  would have recompiled per distinct K.
- The currently-running rPPO runs (olfactory_ambiguity / lindecay) override the scene with **fixed counts**
  (`has_range=False` -> all-active mask, no activation draws), so they don't even exercise the new path.

## Decisions and actions
- No fix needed for rPPO. If **Dreamer** adopts the count-variance feature, keep the same
  reset-all-at-fixed-shape-then-`where` pattern (do NOT size reset arrays to the done/active count) to stay
  recompile-safe — that is precisely the trap [[20260622_1746_dreamer_srl_recompile_storm_done_count]]
  documents.
- Shared cross-session via this insight (backlinked onto the Dreamer recompile insight) + a diary note.
