# Sub-agents that background a driver and return: orphans + idle-ping storms

## Key conclusion
When a sub-agent (general-purpose, developer, senior-developer) launches a long job via `nohup ... &` (or an in-agent background Bash) and then ends its turn, two things happen: (1) the driver keeps running **orphaned** from the agent, and (2) the harness re-emits a "<agent> finished" task-notification each time the agent stops with no live children — producing a stream of near-identical idle pings to the parent. Do not rely on the sub-agent to watch its own background job to completion.

## Evidence, measurements, facts
- Observed 3x this session: a render agent left `/tmp/render_envcount.sh` running and pinged ~10 times "Waiting."; a developer left its acceptance-test sweep running; a senior-developer similarly. Each returned before its background job finished.
- **Fix pattern**: the PARENT owns tracking — launch a lightweight monitor Bash (`until ! kill -0 <driver_pid>; do sleep 30; done; <report>`, `run_in_background: true`) that fires ONE completion notification with the real inventory. This survives the sub-agent exiting.
- To stop the idle pings, `SendMessage` the agent by id with "stop waiting/polling, report final status and terminate; the job is tracked externally." (Watch the id — it was easy to message the wrong agent.)
- Prefer a tracked foreground background-Bash (`bash script > log`, `run_in_background: true`) over `nohup ... &` when you WANT a completion notification: `nohup&` detaches beyond the harness tracker so no auto-notify fires.
- `pkill -f <pattern>` can match its own shell's command line and SIGTERM itself (exit 144); kill by explicit PID instead.

## Decisions and actions
- Adopt parent-side monitors for any sub-agent that hands off a background job; treat repeated idle "completed" pings as noise, not real completion (verify via the monitor / direct state check).
