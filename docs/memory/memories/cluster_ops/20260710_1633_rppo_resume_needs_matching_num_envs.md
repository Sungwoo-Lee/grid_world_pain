# rPPO checkpoint resume works (weights+optimizer+counters) but --num-envs must match the checkpoint

## Key conclusion
Before committing to a long resume-and-extend run, we gate-tested the H1-fixed rPPO resume: it genuinely restores model weights (bit-for-bit), optimizer state (Adam moments/step-count), and step counters, and it is fatal-on-mismatch (no silent train-from-scratch — the H1 failure mode). The load-bearing gotcha: the resume MUST pass `--num-envs` equal to the checkpoint's training num_envs, because the saved `h_state` has shape `(num_envs, hidden)`. A 128-env checkpoint resumed with the global default 128... fine, but with 16 (or vice-versa) Orbax raises a fatal shape mismatch (good fail-fast).

## Evidence, measurements, facts
- Gate test (developer): `restore_rppo_training_state` restored 27 param leaves that matched the raw checkpoint bit-for-bit and differed from random init; Adam step-count 2,548,284 (fresh optimizer = 0); counters episode=10000016, iteration=637071 (not zeroed); end-to-end `train.py --load-checkpoint` resumed and the resumed agent scored survival 100/100 (a random-weight restart would be ~15).
- `src/utils/checkpoint_restore.py` uses `ocp.args.StandardRestore(item=target)` with a live target `{model, optimizer, h_state, key, counters}` → raises on structure/shape/dtype mismatch.
- The checkpoint's `h_state` shape was `(16, 128)` for 16-env runs and `(128, ...)` for 128-env runs — the batch dim IS the training num_envs. Resuming with a different `--num-envs` fatals.
- 128-env runs reached the 10M-episode budget overnight; the earlier 16-env run took ~4 days — episodes accumulate ~8× faster at 8× the envs.

## Decisions and actions
- Launched basic03/04/05 128-env resumes toward 100M with `--load-checkpoint <run>/models --num-envs 128 --episodes 100000000` (verified each log printed the restore-success line resuming from ~10M, not scratch).
