# WandB log_code() ~8-min hang: 'alive' != 'training' — add a progress recheck to launch verification

## Key conclusion
Several lab nodes (observed on 108, 109, 110, 113) intermittently stall for ~8 minutes on `wandb.run.log_code()` — an artifact upload that blocks on an SSL connection to api.wandb.ai — BEFORE the training loop starts. During the hang the `train.py` process is alive, has the correct `--episodes 10000000` budget, and the tqdm bar shows `0/10000000`, but GPU utilisation is 0% and no iterations advance. This matters because the canonical post-launch verification (process count == 1 via pgrep + tqdm `total==10000000`) PASSES during the hang — so passing that check does NOT prove the run is training. Fix the verification: after the 60-90s alive+budget check, do a PROGRESS RECHECK a couple minutes later — re-read the log and confirm the iteration counter (`Iter=N`, episodes done) has ADVANCED and GPU util is high. The hang self-resolves; the durable code fix is to wrap `wandb.run.log_code()` in a timeout / try-except so a slow artifact API cannot block training.

## Evidence, measurements, facts
- Repeated this session: e.g. run w3o8izox (110:1) and u1tyn8xk / fkbk0st7 (113) each sat at 0% util / 0 iterations for minutes, then cleared on their own and trained normally (w3o8izox confirmed at Iter=1277 after ~7 min; fkbk0st7 at Iter=26; etc.).
- The progress recheck is what distinguished a real hang from healthy training — a position/util read via the gpu-status tool ([[20260703_0342_lab_gpu_heterogeneous_probe_contamination]]) plus a log grep for `Iter=`.
- Not a config bug — a transient WandB network issue on the node.

## Decisions and actions
- Standing verification rule: treat a launch as healthy only after a PROGRESS recheck (iterations advancing), not just alive+budget. Background a delayed check (~5-7 min) when a node is known-flaky.
- Deferred code fix flagged to developer: timeout/try-except around `wandb.run.log_code()` in train.py.

## Open questions and follow-ups
