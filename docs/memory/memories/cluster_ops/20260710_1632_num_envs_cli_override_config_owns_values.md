# CLI --num-envs 16 silently shadowed the config's 128 on every launch; fixed with config-owns-values

## Key conclusion
All 6 ladder6 rPPO runs trained with num_envs=16 instead of the intended 128, because a hardcoded CLI `--num-envs 16` flag silently overrode the config default. train.py resolves every such setting as `X = args.X or config.get('training.X')`, so ANY hardcoded launch flag shadows the config. The habit was even documented — the gpu-status skill called `--num-envs 16` the "standard." The config was correct all along (128); it just never reached the trainer. Fix: a config-owns-values convention.

## Evidence, measurements, facts
- `train.py:480` `num_envs = args.num_envs or config.get_mandatory('training.num_envs')`; same `args.X or config` pattern for episodes, checkpoint_frequency, seed, num_steps, lr (lines 400–520, 2460).
- `configs/train/default.yaml:4` `num_envs: 128`. Ground truth of the actual run: the saved run config said 16, and the checkpoint's `h_state` shape was `(16, 128)` (batch dim = num_envs).
- The original basic03 launch log printed `num_envs: 128` (config) but `Parallel Envs: 16` (actual), with `Total Timesteps = 10M × 500 × 16`.
- The `.claude/skills/gpu-status/SKILL.md:30` line read "standard rPPO/Dreamer runs ... `--num-envs 16`" — the likely source of the habit.
- **rPPO vs Dreamer train-config split** (why their values differ): rPPO merges `configs/train/recurrent_ppo.yaml` on top of `default.yaml` (checkpoint_frequency 200000, log_interval 500, max_checkpoints_to_keep null); Dreamer reads `default.yaml` alone (10000 / 10 / 20). There is NO dreamer-specific train config.
- 128 envs reaches 10M episodes ~8× faster than 16 (overnight vs ~4 days).

## Decisions and actions
- gpu-status skill fixed: num_envs 16 → 128, "do NOT override to 16" (commit `944faab`).
- config-owns-values convention landed (commit `0104d3c`): num_envs / seed / checkpoint_frequency are config-owned **per-algorithm** (rPPO layers recurrent_ppo.yaml; Dreamer uses default.yaml) — do NOT pass them as launch boilerplate, only as a flagged one-off deviation. `--episodes` stays always-explicit (config default `100` is a deliberate smoke-test safety placeholder). Updated the training-runner profile + both launch templates' guidance; **no config value changes** (an initial wrong instruction to bump default.yaml checkpoint_frequency 10000→100000 was reverted — that value is Dreamer's).
- Terminated all 16-env rPPO runs and relaunched the 6-level ladder fresh at `--num-envs 128`.

## Open questions and follow-ups
