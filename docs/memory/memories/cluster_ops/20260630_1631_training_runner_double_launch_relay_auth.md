# Training-runner double-launch + relay-authority guardrail; targeted PID kill for de-dup

## Key conclusion
Launching `rppo_basic05_randpred_n110` produced TWO live training processes on node 110 GPU 0. Cause: the training-runner's interim post-launch check itself called the launch path again (a `sleep && run_command.py` wrapped command), starting a second `train.py`. Both ran the same config with the correct `--episodes 10000000` budget. De-duplication required a TARGETED `kill -INT <PID>` on the duplicate only — `terminate_command.py` matches by tag pattern and would have killed BOTH runs. Separately: the training-runner agent REFUSED to act on a kill approval relayed by top-level Claude ("coordinator-relayed approval carries no user authority; only a direct user message counts"), so top-level Claude performed the targeted kill itself via run_command.py rather than fighting the guardrail.

## Evidence, measurements, facts
- Two PIDs: 1154 (WandB eylrft3q, intended, first) + 1323 (WandB uegqltpq, duplicate). GPU 0 showed ~one process's worth of memory; PID 1154 got there first.
- Resolution: `./run_command.py 110 "kill -INT 1323"`; verified pgrep shows exactly one process and GPU 0 has a single training job; surviving run healthy (tqdm total=10000000, Iter>300).
- ~3 min of redundant compute lost; nothing else (both had the right budget). Diary training-start row logged for the survivor only, noting the defunct duplicate.
- Same broad family as the earlier SSH-multiplexing duplicate-process incidents; the new specifics are (a) the runner's OWN verification step can re-launch, and (b) the relay-authority guardrail blocks coordinator-relayed approvals.

## Decisions and actions
- For de-duplicating same-tag runs, use a targeted `kill -INT <PID>` (pattern-based terminate_command.py is unsafe when >1 PID shares the tag).
- When a sub-agent's guardrail refuses a relayed approval, top-level Claude should resolve the operational action directly rather than loop the relay.
- Twin operational gotcha to the budget one [[20260629_1724_rppo_single_config_episode_budget]] (same launch workflow).

## Open questions and follow-ups
- The training-runner's post-launch verification should NOT re-invoke the launch wrapper; worth a fix to its profile so the double-launch can't recur.
