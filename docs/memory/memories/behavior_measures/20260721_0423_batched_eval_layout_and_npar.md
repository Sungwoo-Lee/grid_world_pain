# Batched-eval output layout + NPAR tuning for probe sweeps

## Key conclusion
When wiring the fast `eval_rollout.py --batched` path into a distributed Dreamer probe sweep, two things differ from the old single-env `dreamer_srl_probe_eval.py` driver and will silently break a naive port: (1) **output layout** - the unified `eval_rollout.py` writes recordings to `{output-root}/{run_tag}/{ckpt}/recordings/{ckpt}/episode_*.rec.gz`, one nesting level DEEPER than the old driver's flat `{output-root}/recordings/{ckpt}/...`, so an aggregator that globs the flat path finds nothing; fix with a **layout-agnostic recursive glob** (`glob.glob(f"{epdir}/**/episode_*.rec.gz", recursive=True)`). (2) **parallelism** - the batched path is HEAVIER per process than single-env because its `vmap` over 30 envs parallelises across cores even with `intra_op_parallelism_threads=1` and `--xla_cpu_multi_thread_eigen=false`; running NPAR=14 batched processes drove a 20-core node to load 142. The right batched NPAR is **~4-6 per node**, not the ~18 used for single-env.

## Evidence, measurements, facts
- Layout: a batched gap-fill wrote 148 cells that the aggregator missed because its glob expected `{epdir}/recordings/*/...`; the actual path was `{epdir}/{run_tag}/{ckpt}/recordings/{ckpt}/...`. Recursive glob fixed it (148 -> 0 missing).
- NPAR: node 103 with NPAR=14 batched hit load 142 (thrashing) while still completing; single-env at NPAR=18 sits ~load 20. Batched at ~NPAR=5 would keep load near core count.
- Both were found during the first production use of batched eval (an xl gap-fill of the basic04 Dreamer size sweep), not on a full sweep - cheap place to discover them.

## Decisions and actions
- Patched `tmp/aggregate_dreamer_metrics.py` to use the recursive glob (also made it MERGE existing CSV rows so incremental runs do not drop prior points).
- Built `tmp/dist_dreamer_worker_batched.sh` that calls `eval_rollout.py --batched`; next full batched sweep must drop NPAR to ~4-6.

## Open questions and follow-ups
- The batched worker's default NPAR should be lowered to ~5 before it is promoted into `scripts/` for production.
